## 1단계: 변경사항 분석

변경된 파일 목록:
  1. 새 파일 추가: src/services/authService.ts
     - 사용자 로그인 함수 구현
     - JWT 토큰 처리
     - 에러 핸들링

  2. 새 파일 추가: src/services/__tests__/authService.test.ts
     - authService 단위 테스트 작성
     - 로그인 성공/실패 케이스
     - 토큰 저장 확인

변경사항의 성격: 여러 범주 혼합 (기능 추가 + 테스트 추가)


## 2단계: 각 변경사항별 타입 분류

  • src/services/authService.ts
    타입: feat (새로운 기능 추가)
    근거: 새로운 인증 서비스 모듈을 추가하는 새로운 기능

  • src/services/__tests__/authService.test.ts
    타입: test (테스트 추가)
    근거: 인증 서비스 단위 테스트를 추가

  ✓ 가장 영향도 높은 범주: feat
    (feat와 test가 함께 있을 경우, feat이 주된 변경사항으로 선택)


## 3단계: 한국어 커밋 메시지 2개 제안

┌─────────────────────────────────────────────────────────────────────────────┐
│ [제안 1] 통합 커밋 (한 개의 커밋으로 처리)                                    │
└─────────────────────────────────────────────────────────────────────────────┘

feat(auth): 사용자 인증 서비스 구현 및 테스트

새로운 인증 서비스 모듈을 구현합니다.

- authService.ts: JWT 기반 사용자 로그인 함수, 토큰 처리, 에러 핸들링
- authService.test.ts: 로그인 성공/실패 케이스 및 토큰 저장 검증 테스트

이 변경사항으로 사용자 인증 기능이 완벽하게 구현되고 테스트됩니다.


┌─────────────────────────────────────────────────────────────────────────────┐
│ [제안 2] 분할 커밋 (2개의 커밋으로 분리)                                      │
└─────────────────────────────────────────────────────────────────────────────┘

커밋 1:
  feat(auth): 사용자 인증 서비스 구현

  JWT 기반 사용자 로그인 함수, 토큰 처리, 에러 핸들링을 포함하는
  새로운 인증 서비스 모듈을 구현합니다.

커밋 2:
  test(auth): 인증 서비스 단위 테스트 추가

  authService의 로그인 성공/실패 케이스와 토큰 저장을 검증하는
  단위 테스트를 추가합니다.


## 4단계: 다중 커밋 시나리오 설명

┌─────────────────────────────────────────────────────────────────────────────┐
│ 시나리오 A: 통합 커밋 (권장도: ⭐⭐⭐)                                         │
└─────────────────────────────────────────────────────────────────────────────┘

방식:
  - 1개의 커밋으로 authService.ts와 authService.test.ts를 함께 커밋
  - 타입: feat (feat가 test보다 영향도 높음)

장점:
  ✓ 커밋 히스토리가 간결함
  ✓ 기능과 테스트가 함께 진행되는 의도가 명확함
  ✓ 한 번의 원자적 변경사항으로 처리

단점:
  ✗ 한 커밋에 여러 타입 포함 (feat + test)
  ✗ git log에서 타입이 feat로만 보임

사용 상황:
  - 기능과 테스트가 밀접하게 관련되어 있을 때
  - 커밋을 하나의 완성된 단위로 보고 싶을 때
  - 간결한 히스토리 선호


┌─────────────────────────────────────────────────────────────────────────────┐
│ 시나리오 B: 분할 커밋 (권장도: ⭐⭐⭐⭐)                                        │
└─────────────────────────────────────────────────────────────────────────────┘

방식:
  - 커밋 1: feat - 인증 서비스 구현 (src/services/authService.ts)
  - 커밋 2: test - 테스트 추가 (src/services/__tests__/authService.test.ts)

장점:
  ✓ 각 커밋의 의도가 명확함 (feat vs test 구분)
  ✓ git blame이 더 정확함
  ✓ 특정 커밋을 되돌려야 할 경우 유연성 높음
  ✓ 코드 리뷰할 때 기능과 테스트를 분리해서 검토 가능

단점:
  ✗ 커밋 히스토리가 더 많음
  ✗ feat 커밋만으로는 불완전한 상태 (테스트 없음)

사용 상황:
  - 기능 구현과 테스트를 명확히 분리하고 싶을 때
  - 각 커밋이 하나의 명확한 의도를 가져야 할 때
  - 세밀한 히스토리 추적이 필요할 때

추천:
  이 경우 분할 커밋(시나리오 B)을 권장합니다.
  이유: 인증 서비스는 중요한 기능이므로, 구현과 테스트를 명확히 분리하여
       각 변경사항의 의도를 명확하게 드러내는 것이 좋습니다.
