4단계: 다중 커밋 시나리오 제안
================================================================================

【권장 시나리오: 다중 커밋 (5개 분할)】

이유:
1. 각 변경사항의 목적이 명확하게 다름
2. 각 타입이 별도의 Conventional Commits 규칙을 적용받음
3. Git 히스토리에서 각 변경의 의도가 분명함
4. 향후 revert, blame, bisect 작업이 용이함

커밋 순서 (권장):
  1순위: fix(Modal): Modal 컴포넌트 접근성 개선
         → 버그 수정은 최우선으로 적용 (영향도: 높음)

  2순위: test: 통합 테스트 추가
         → 버그 수정 직후 관련 테스트 추가 (영향도: 중간)

  3순위: refactor(utils): 사용되지 않는 함수 제거
         → 코드 정리 (영향도: 중간)

  4순위: style(global): 들여쓰기 및 포매팅 개선
         → 스타일 정리는 가장 마지막 (영향도: 낮음)

  5순위: docs: 설치 방법 및 사용법 문서 추가
         → 문서는 모든 코드 변경 후 마지막에 추가 (영향도: 중간)

【대체 시나리오: 단일 커밋 (모두 합침)】

불가능함. 이유:
- 변경사항이 5개 독립적인 범주에 분산
- 하나의 주요 목적으로 통합 불가능
- 단일 커밋으로 표현하면 git 히스토리 가독성 저하

【대체 시나리오: 2-3개 그룹 커밋】

그룹 1: 버그 수정 + 테스트
  fix: Modal 컴포넌트 접근성 개선 및 통합 테스트 추가

그룹 2: 코드 정리 (refactor + style)
  refactor: 코드 정리 및 포매팅 개선

그룹 3: 문서
  docs: 설치 방법 및 사용법 문서 추가

평가: 덜 권장함 (각각을 분리하는 것이 더 명확)
