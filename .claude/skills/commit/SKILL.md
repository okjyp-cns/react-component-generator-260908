# commit: 변경사항 자동 분석 및 커밋

현재 작업 디렉토리의 git 저장소에서 **스테이징된 변경사항**을 읽고, Conventional Commits 형식의 한국어 커밋 메시지를 생성한 뒤 사용자 승인 후 커밋합니다.

## 워크플로우

### Step 0: 저장소 지침 로드

작업 시작 전 저장소 루트의 `AGENTS.md` (없으면 `CLAUDE.md`)를 찾아 읽습니다. 있으면 커밋 컨벤션, 타입 선택 규칙, 메시지 스타일을 이후 전 과정에서 따릅니다.

### Step 1: 변경사항 확인

```bash
git status
git diff --cached
```

다음 상태를 판단합니다:

- **스테이징된 변경이 있는가?** 없으면 사용자에게 알리고 스테이징할 파일을 제안한 뒤 종료합니다.
- **언커밋 변경이 있는가?** (스테이징되지 않은 변경) 있으면 경고하고 계속 진행할지 확인받습니다. `--auto` 모드에서는 언커밋 변경이 있으면 진행하지 않고 종료합니다.
- **파일 상태**: 추가(A), 수정(M), 삭제(D), 이름변경(R)에 따라 커밋 타입을 결정합니다.

### Step 2: 변경사항 분석

스테이징된 파일들의 diff를 분석합니다:

1. **영역별 분류**: 수정된 파일들을 도메인·기능별로 논리적 단위로 분류합니다.
   - 예: `src/components/` 변경, `server/` 변경, `test/` 변경이 섞여 있으면 각각 구분

2. **커밋 타입 결정** (Conventional Commits):
   - `feat`: 새 기능 추가 (파일·함수·기능 신규)
   - `fix`: 버그 수정
   - `refactor`: 기능 변경 없는 코드 개선 (구조·네이밍·변수 추출 등)
   - `test`: 테스트 추가·수정
   - `docs`: 문서 추가·수정
   - `chore`: 빌드·의존성·설정 변경 (package.json, tsconfig, eslint 등)

3. **변경 내용 요약**: 각 파일의 변경을 간단히 정리합니다.
   - 예: `src/App.tsx: 버튼 클릭 핸들러 추가`

### Step 3: 커밋 메시지 생성

변경사항 분석 결과를 바탕으로 커밋 메시지를 생성합니다.

**기본 형식** (Conventional Commits + 한국어):

```
feat: 로그인 기능 구현

- 이메일 검증 로직 추가
- 토큰 기반 세션 관리 구현
- 에러 핸들링 보강
```

**규칙**:
- **제목**: `<type>: <한국어 요약>` (50자 이내)
  - 한국어만 사용 (영어 섞지 않기, 기술 용어 제외)
  - 마침표 없음
  - 예: `feat: 럭셔리 스타일 랜딩 페이지 추가` (O), `feat: Add luxury landing page` (X)

- **본문** (선택):
  - 제목으로 설명 부족한 변경은 본문에 기술
  - 왜(why), 무엇(what)을 중심으로 작성
  - 각 항목 앞에 `-` 또는 `*` 사용
  - 한국어 문법 유지

- **Breaking change** (있으면):
  ```
  BREAKING CHANGE: API 반환 형식이 변경됨
  ```

**다중 커밋 분할**:

변경사항이 여러 논리적 단위로 명확히 구분되면 여러 커밋으로 분할 제안:

- 각 커밋이 독립적으로 동작하는가?
- 각 커밋이 하나의 기능/버그를 다루는가?

분할 가능하면 사용자에게 제안합니다 (예: 기능 추가 1개 + 테스트 추가 1개).

### Step 4: 사용자 확인 (기본 모드)

생성된 커밋 메시지를 사용자에게 제시합니다:

```
커밋 메시지:

feat: 럭셔리 스타일 랜딩 페이지 추가

- 헤로 섹션 (비디오 배경, 텍스트 오버레이) 구현
- 기능 카드 섹션 추가
- 풀 반응형 디자인 적용

파일 변경:
  M src/App.tsx (50 insertions, 10 deletions)
  A src/components/LandingPage.tsx (200 lines)
  M src/App.css (80 insertions)

선택:
  1. 승인 후 커밋
  2. 메시지 수정
  3. 분할 커밋 제안 보기
  4. 취소
```

사용자 선택:

- **승인**: Step 5로 진행
- **수정**: 메시지 편집 → Step 5
- **분할 보기**: 분할 제안 출력, 동의하면 각각 커밋
- **취소**: 변경 없음, 종료

### Step 5: 커밋 실행

`git commit -m "<message>"` 실행:

```bash
git commit -m "$(cat <<'EOF'
feat: 럭셔리 스타일 랜딩 페이지 추가

- 헤로 섹션 (비디오 배경, 텍스트 오버레이) 구현
- 기능 카드 섹션 추가
- 풀 반응형 디자인 적용

Co-Authored-By: Claude Haiku 4.5 <noreply@anthropic.com>
EOF
)"
```

**결과**:
- 성공: "✓ 커밋 완료: abc1234" + 커밋 메시지 출력
- 실패 (pre-commit hook): 에러 메시지 출력, 사용자가 수정 후 다시 커밋하도록 안내

### Step 6: `--auto` 모드

`--auto` 플래그가 있으면 사용자 확인 없이 자동으로 진행합니다:

1. **언커밋 변경 확인**: 있으면 진행하지 않고 스테이징하도록 안내 후 종료
2. **메시지 생성 및 커밋**: 생성된 메시지로 바로 커밋
3. **결과 보고**: 커밋 완료 또는 실패 사유 출력

## 참고

- **스테이징 방법**:
  ```bash
  git add <파일>           # 특정 파일 스테이징
  git add -A              # 모든 변경 스테이징
  git add -p              # 대화형 스테이징
  ```

- **커밋 제목 길이**: 50자 이내 추천 (git log --oneline과의 호환성)

- **lint/test 확인**: 커밋 전 `bun run lint`, `bun run test` 실행을 권장합니다 (자동 실행하지 않음).

- **Pre-commit hook**: 저장소에 pre-commit hook이 있으면 자동으로 실행되며, 실패 시 커밋이 중단됩니다. Hook 오류를 수정한 후 다시 커밋하세요.

## 보안 규칙

- **Co-Authored-By 행**: Claude 협업 신용 표기는 자동 추가 (항상 포함)
- **시크릿 제외**: 환경 변수, API 키, 토큰이 diff에 포함되면 경고하고 커밋하지 않습니다
- **임시 파일**: .env, 로그 파일, node_modules 등이 스테이징되면 경고합니다
